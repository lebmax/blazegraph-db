# Kill follower во время LOAD

## Воспроизведение

На `163a813` тест `TestHA3JustKills.testABC_LiveLoadRemainsMet_kill_B`
проверяет незавершённость конечной LOAD после `Thread.sleep(2000)`.
Диагностический запуск показывает POST на отметке 10216 мс, HTTP 200 на
12130 мс и успешный `Future.get()` на 12162 мс. Следующий `assertFalse`
падает до kill. Причина — предположение о длительности загрузки: она успешно
закончилась за 1914 мс, раньше проверки (P≈0,99). Такой же код есть в
`testABC_LiveLoadRemainsMet_kill_C`.

Оба теста используют существующий `ControlledLoadTask` из
[исправления rejoin во время LOAD](2026-11-08-load-rejoin-synchronization.md).
После трёх исходных FOAF-файлов тот же SPARQL UPDATE читает управляемый
N-Triples HTTP-источник. Тест ждёт фактического чтения источника и удерживает
EOF до восстановления двухузлового pipeline, members и joined. До и после
kill Future должен оставаться незавершённым, token — прежним. Затем тест
разрешает EOF, требует успешного завершения LOAD и равенства digest журналов
оставшихся узлов. Try-with-resources закрывает источник и отменяет задачу
при ошибке. Проверки не зависят от того, сколько занимает конечный набор данных.

Ожидание pipeline учитывает `getZKSessionTimeout() + awaitQuorumTimeout`
в миллисекундах: в текущей конфигурации это 20000 + 10000 = 30000 мс.
Прежний предел B в 10000 мс истёк до обнаружения отказа. Это ограниченное
ожидание с запасом на обработку событий, а не гарантия ZooKeeper о верхней
границе восстановления.

## Ошибка атрибуции отказавшего узла

Управляемая LOAD выявила вторую причину сбоя. Лидер A сохраняет proxy B
для отправки блока; до возврата ошибки запроса ZooKeeper удаляет B и меняет
топологию на A→C. `launderPipelineException()` определял виновника по
текущему соседу и принудительно удалял исправный C. Quorum распадался,
коммит индексов завершался ошибкой, LOAD возвращал HTTP 500.

В запуске `20261108-kill-load-session-bound-pair`:

- в 18:24:53.989 A начинает отправку в B, затем получает ошибку сокета;
- в 18:24:54.015 наблюдается удаление B и смена pipeline;
- в 18:24:56.038 обрабатывается ошибка RMI к B (`9081`);
- в 18:24:56.041 A ошибочно вызывает force-remove для C;
- C выходит при двух оставшихся joined-узлах, после чего теряется quorum.

Логи C не показывают его самостоятельного отказа до принудительного удаления.
Последовательность и исходный код подтверждают неверную атрибуцию (P≈0,99).

`PipelineState` теперь хранит UUID вместе с proxy и адресом downstream.
Лидер и промежуточный follower передают обработчику UUID именно той попытки,
которая завершилась ошибкой. Текущий upstream остаётся диагностическим
контекстом; текущий downstream не используется для назначения виновника.
Обработка вложенной ошибки другого follower сохранена. Приватный локальный
holder стал неизменяемым; его неиспользуемая сериализация удалена. Публичные
RMI-сообщения и форматы журналов не изменены.

Первый положительный парный запуск повторил тот же порядок событий:
ZooKeeper удалил B в 18:38:28.011, ошибка RMI обработана в 18:38:29.168,
force-remove и reset указали B. C сохранил участие, LOAD вернул HTTP 200,
digest A/C совпал. Отдельный mock helper не добавляется: интеграционный
red/green проверяет фактическую передачу, смену topology и завершение коммита.

`C:\Users\Axiom\.jdks\axiomjdk-1.8.0_482`; ZooKeeper из Docker-проекта
`blazegraph-e0`, River и HA-процессы — на той же JDK.

Расширенный HA-набор включает все семь `TestHA3JustKills`, один
`TestKillTrigger`, три `TestControlledLoadSource` и четыре rejoin во время
LOAD из `TestHA3JournalServer`. В промежуточном варианте upstream брался из
`IHASendState`, который пересылается без изменения и на длинном pipeline
может обозначать лидера. Окончательный вариант сохраняет прежний способ
получения диагностического upstream с обработкой отсутствующего local member;
UUID виновника в обоих вариантах берётся из снимка proxy. После этой правки
тот же расширенный HA-набор повторно прошёл полностью.

Девять core-проверок: передача и stress для двух узлов; передача, checksum и
смена pipeline для малого/большого сообщения на трёх узлах; WORM/RW с двумя
буферами и тремя участниками; reset отсутствующего в pipeline участника.
Все девять тел выполнены, retry events и skipped отсутствуют. В core POM
сохраняется штатная настройка двух автоматических повторов, но в этом запуске
они не потребовались. Сообщений `Test did not release buffer(s)` нет.

На окончательном коде прошли 24 разных теста: 15 HA и 9 core, без failures,
errors, skipped и повторов. Оба simple kill-сценария прошли также в отдельной
паре до уточнения upstream. `verified-inputs.json` окончательного HA-запуска,
как и файл core-запуска, содержит SHA-256 проверяемых исходников и core JAR;
core JAR из classpath HA совпадает с результатом сборки.
Полный HA/scale-out aggregate в рамках этого исправления не запускается.
