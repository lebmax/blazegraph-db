# Ожидание асинхронного удаления HALog

## Причина

В сохранённом `20261108-ha-final-recheck` сценарий
`TestHA3JournalServer.testStartAB_C_MultiTransactionResync_5tx_then_50ms_delay`
падает в `assertHALogNotFound`: HALog с commit counter 1 ещё существует на B.
Два новых запуска неизменённого сценария (`20261108-halog-purge-red` и
`20261108-halog-purge-repro-2`) прошли. Первый каталог, несмотря на имя `red`,
не содержит воспроизведения падения.

`HALogNexus.deleteHALogs()` отправляет удаление в executor. При штатном
`HAJournalServer.ConfigurationOptions.DEFAULT_HA_LOG_PURGE_TIMEOUT = 0`
commit не ждёт завершения удаления. Комментарий в `deleteHALogs()` прямо
предупреждает о старых тестах, предполагающих синхронный purge. Между commit и
удалением допустимо увидеть ещё существующий исторический HALog. Немедленная
проверка отсутствия файла не соответствует этому контракту (**P≈0,99**).

Локальная регрессия воспроизводит ту же ошибку без зависимости от планирования
потоков: сервис дважды возвращает digest существующего HALog, затем сообщает
`FileNotFoundException`. Старый helper падает уже на первом ответе. Отдельная
регрессия показывает, что старый helper также проглатывает прочие `IOException`,
принимая сбой соединения за отсутствие файла.

## Изменение

`assertHALogNotFound()` повторяет запрос только при подтверждённом существовании
файла. Интервал опроса — до 10 мс, общий бюджет ожидания для диапазона commit
counters и всех сервисов — 5 с. Это ограничение ожидания между синхронными RPC;
оно не задаёт отдельный timeout для самого RPC.

Успехом считается только `FileNotFoundException`, включая обёрнутую причину.
Прочие `IOException` пробрасываются. Если файл остаётся, проверка завершается
ошибкой; прерывание ожидания вызывает `InterruptedIOException` с сохранением
interrupt-флага. Настройки и реализация purge сервера не меняются.

В штатный HA aggregate добавлены пять `TestHALogPurge` cases: отложенное удаление,
обёрнутый `FileNotFoundException`, ошибка соединения, постоянно существующий
HALog и прерывание. Подсчёт `suite().countTestCases()` даёт 159 случаев HA и
484 случая в составе кластерного runner; это подсчёт, а не полный запуск.

## Проверка

Все приведённые запуски выполнены на Axiom JSC `1.8.0_482-b10` из
`C:\Users\Axiom\.jdks\axiomjdk-1.8.0_482`. Артефакты сохранены вне `target`,
под `C:\Users\Axiom\OpenideProjects\blazegraph-artifacts\cluster`.

| Запуск | Tests | Failures | Errors | Автоматические повторы |
| --- | ---: | ---: | ---: | ---: |
| `20261108-halog-wait-unit-red-5`: новые unit cases со старым helper | 5 | 3 | 0 | 0 |
| `20261108-halog-wait-family-green`: новые unit cases и шесть вариантов resync | 11 | 0 | 0 | 0 |
| `20261108-halog-wait-callers-green`: остальные восемь интеграционных callers | 8 | 1 | 0 | 0 |
| `20261108-halog-wait-repeat`: отдельный повтор 50 мс и LiveResync | 2 | 1 | 0 | 0 |

Отрицательный контроль выполнялся отдельным `javac`/JUnit-запуском с прежним
скомпилированным helper. Он выявил гонку, проглатывание ошибки соединения и
неправильный результат при прерывании. После изменения модуль `bigdata-ha-test`
пересобран и установлен Maven на указанной JDK; интеграционные проверки
запускаются через `Run-ClusterTests.ps1 -TestSet HA -SkipBuild -HATest ...`.
Фактический состав выбранных методов проверяется по свежим Surefire XML.

В расширенном наборе не прошёл `testStartAB_C_LiveResync`: `assertReady()`
получил `NotReady`. Эта проверка находится до вызова `assertHALogNotFound()`;
тест был первым в выбранном наборе. Он не дошёл до изменённого helper.
Название каталога `callers-green` не означает успешный результат. Точный
механизм потери готовности пока неизвестен. В отдельном повторе сценарий с
задержкой 50 мс снова прошёл, а LiveResync снова упал в `assertReady()`.
Этот симптом требует отдельного расследования; он не считается успешно
прошедшим после повтора.

Таким образом, проверены 19 различных случаев: пять новых unit cases и все
14 интеграционных callers изменённого helper. Прошли 18; LiveResync дважды
упал до проверки HALog. Ошибок `HALog exists` после изменения не получено.
Это адресная проверка, а не подтверждение отсутствия всех HA-сбоев.

Последующий [разбор LiveResync](2026-11-08-live-resync-readiness.md) установил
гонку между наблюдением service join и локальной готовностью C. Результаты
этого отдельного исправления приведены в новом отчёте; исходные итоги выше
сохранены.

Полный HA aggregate в рамках этого изменения не запускается. Четыре ранее
обнаруженных падения ожидания quorum во время LOAD из
[отчёта восстановления](2026-11-08-cluster-restoration.md) требуют отдельного
разбора; это изменение не подтверждает их исправление.
